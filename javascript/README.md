# JavaScript Data Source Sample

This sample shows how Kubling loads a JavaScript data source from a generated module bundle. It is deliberately self-contained: the JavaScript module returns deterministic task documents and does not call an external API.

The sample demonstrates:

- a `SCRIPT_DOCUMENT_JS` data source;
- a module-owned DDL and translator configuration;
- automatic table-handler discovery;
- imports between JavaScript module files;
- the injected `queryFilter`, `resultSet`, `insertOperation`, and `affectedRows` objects; and
- descriptor and module bundles generated by the official Kubling CLI.

JavaScript is intentional here because it is the capability being taught. Provider-backed samples should use `PROVIDER_GRPC`; start with the [Quickstart](../quickstart/README.md) for that architecture.

The relevant source files are intentionally few:

- `descriptor/vdb/JavaScriptVDB.yaml` registers the JavaScript data source and loads its DDL from the module;
- `module/bundle-script-info.yaml` declares the module metadata and handler directory;
- `module/handler/TASK.js` implements the table operations; and
- `module/data/tasks.js` provides deterministic documents through a normal JavaScript import.

## Prerequisites

- Git
- Docker Engine
- Docker Compose v2

No JavaScript runtime, Node.js, Java, database, provider, or credentials are required on the host.

## Start

```bash
cd javascript
docker compose up --wait
```

Compose uses exact image versions and runs Kubling CLI to generate two local artifacts in a named volume:

- `javascript-descriptor.zip`
- `javascript-module.zip`

They are runtime build output and are never written to the repository.

When Compose reports the stack as ready:

- Kubling Studio: <http://localhost:8282/console>
- Health endpoint: <http://localhost:8282/observe/health>
- VDB: `JavaScriptVDB`
- schema/data source: `javascript`
- table: `TASK`

## Query

Open Kubling Studio and run:

```sql
SELECT id, title, priority, completed
FROM javascript.TASK
ORDER BY id;
```

Expected rows:

| id | title | priority | completed |
|:--|:--|--:|:--|
| `task-1` | Learn module bundles | 1 | `true` |
| `task-2` | Inspect queryFilter | 2 | `false` |
| `task-3` | Handle a mutation | 3 | `false` |

`handler/TASK.js` returns the documents through the injected `resultSet`. Kubling applies sorting because the module declares that sorting is not pushed down to the JavaScript source.

## Mutation

Run:

```sql
INSERT INTO javascript.TASK (id, title, priority, completed)
VALUES ('task-example', 'Created through SQL', 4, false);
```

Expected result:

```text
affectedRows: 1
```

The handler validates the document received through `insertOperation.jsonList` and increments `affectedRows`. The sample is intentionally stateless, so the inserted row is acknowledged but not retained. A real adapter would call its owning system before incrementing the counter.

## Automated verification

Run the same query and mutation assertions used by CI:

```bash
docker compose --profile test run --rm --no-deps smoke-test
```

Static checks are available from the repository root:

```bash
bash scripts/check-javascript.sh
```

## Cleanup

```bash
docker compose down --volumes --remove-orphans
```

This removes Kubling, the test container, and the generated descriptor/module volume.
